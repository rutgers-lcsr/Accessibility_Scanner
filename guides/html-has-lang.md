## What this means

The page's `<html>` tag has no `lang` attribute. A screen reader picks a voice and pronunciation from that attribute; without it, it uses the user's default, and an English page read with French rules is barely understandable. Browsers also use it for hyphenation, quotes and translation offers.

## Why it matters

One attribute on one tag, and it affects every word on the page. WCAG 3.1.1 (Language of Page).

## Before

```html
<!DOCTYPE html>
<html>
```

## After

```html
<!DOCTYPE html>
<html lang="en">
```

Use the code of the language the page is written in: `en`, `es`, `zh`. A page that is mostly English with a Spanish paragraph keeps `lang="en"` and marks the paragraph with `<p lang="es">`.

## WordPress

- `header.php` should print the tag as `<html <?php language_attributes(); ?>>`; if the theme hard-codes `<html>`, fix that line in a child theme. Block themes do this already.
- The value comes from **Settings → General → Site Language**; set it to the language the site is written in.

## Canvas

Canvas sets the language on its own pages, so a failing page here is Canvas's own interface. Mark the finding **Accepted** with the note "Canvas interface" and report it to the Rutgers Canvas team. Content in the editor cannot change it.

## GitHub Pages

Set it in the layout:

```liquid
<html lang="{{ site.lang | default: "en" }}">
```

and add `lang: en` to `_config.yml`. Most remote themes already print `lang` from `site.lang`, so often the config line alone is the fix. If your theme's layout hard-codes `<html>`, copy `_layouts/default.html` into your repository and change it.

## Plain HTML

Add `lang="en"` (or the right code) to the `<html>` tag in every page, or in the shared head include or template. Pages generated by a script should get it from the template.

## Check your fix

Use the **Rescan this page** action next to any affected page once your change is live. A layout fix clears every page that uses it.
